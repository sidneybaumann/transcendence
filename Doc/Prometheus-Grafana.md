# Infrastructure
Reading `docker-compose.dev.yml` and `prometheus.yml` is useful for understanding how the monitoring stack is set up.
Prometheus collects metrics from hardware, docker, database and app. Grafana uses Prometheus as a data source to visualize them.
```
node-exporter       = hardware metrics
cadvisor            = container metrics
postgres-exporter   = DB metrics
app                 = app metrics
                          ↓
                      Prometheus   → alertmanager → discord
                          ↓
                        Grafana
                          ↑
                      User's eyes
```

# Mini-guide

1. Expose metrics for your app
- Install, register, and configure fastify metrics to expose metrics on `/metrics`
- Start the app and verify you can see metrics at `http://localhost:3000/metrics`

2. Configure the Prometheus collector
- Write `prometheus.yml` to scrape `/metrics` from your application service at `app:3000`
- Add a new `prometheus` service (do not use the latest image) to docker-compose, mapping port 9090 to 9090
- Start the Prometheus container. Verify `http://localhost:9090/` and that the target (app) is UP.

3. Configure the Grafana visualizer
- Add a new `grafana` service to docker-compose with port 3000 mapped to 3001 (port 3000 is already used by the server)
- Add Prometheus as a datasource
- Import the pre-made dashboard ID: 11159

4. Add exporters to your docker-compose:
- postgres-exporter
- node-exporter
- cadvisor
Update `prometheus.yml` to scrape each of them.

5. Alerting system
- Write `alert_rules.yml` and add it to `prometheus.yml`
- Write `alertmanager.yml` (or configure it via docker-compose)

6. Make your custom dashboard

7. Provision dashboards and datasources for Grafana


# Queries of our custom dashboard

## Row 1. Health and Connectivity

These queries tell you if your targets are actually alive.

* **`pg_up`**: This is a specific metric usually exported by the **PostgreSQL Exporter**. 
    * **Value 1**: The exporter can successfully connect to the PostgreSQL database.
    * **Value 0**: The database is down or unreachable.
* **`up`**: This is a default metric generated by Prometheus itself for every target it scrapes.
    * **Value 1**: The last "scrape" (data collection) was successful.
    * **Value 0**: Prometheus couldn't reach the exporter/service.


## Row 2. Application Performance (Traffic & Latency)

This is where you see how your "beautiful server" is handling the heat.

### Requests Per Second (Throughput)
`sum(rate(http_request_duration_seconds_count{job="our_beautiful_server"}[5m])) by (status_code, route)`

* **`rate(...[5m])`**: Calculates the per-second average increase of the request counter over the last 5 minutes.
* **`sum(...) by (status_code, route)`**: This aggregates the data. Instead of seeing a line for every single instance/pod, you see the total traffic grouped by the HTTP status (e.g., 200, 404, 500) and the specific URL path (route).
* **Plain English**: "Show me the total requests per second for each route, broken down by success/failure."

### 95th Percentile Latency ($P_{95}$)
`histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{job="our_beautiful_server"}[5m])) by (le, route))`

* **`http_request_duration_seconds_bucket`**: Histograms in Prometheus don't store exact timings; they store counts of requests that fell into specific "buckets" (e.g., "requests under 0.5s", "requests under 1s").
* **`le`**: This stands for "less than or equal to." It's the label used to define bucket boundaries.
* **`histogram_quantile(0.95, ...)`**: This is the "magic" function. It looks at the buckets and calculates the response time that 95% of your users are experiencing or better.
* **Plain English**: "What is the maximum time the fastest 95% of my users waited over the last 5 minutes, per route?"

## Row 3. Container Resource Monitoring

These queries typically come from **cAdvisor** to tell you how your Docker/Kubernetes containers are breathing.

* **`container_memory_working_set_bytes{name!=""}`**
    * Shows the amount of RAM currently in use by containers. 
    * **Why "Working Set"?** This is the metric the OOM (Out Of Memory) killer uses to decide which container to terminate. It includes cached memory that cannot be easily released.
    * `name!=""` ensures you are looking at actual named containers and not root cgroups.

* **`sum(rate(container_cpu_usage_seconds_total{name!=""}[5m])) by (name) * 100`**
    * **`rate(...[5m])`**: Since CPU usage is a counter of "seconds spent processing," the rate gives you "seconds per second."
    * **`* 100`**: Converts that rate into a percentage. 
    * **Note**: If a container has 4 cores and is pinned at 100% on all of them, this query will return **400**.

* **`sum(rate(container_network_receive_bytes_total{name!=""}[5m])) by (name)`**
    * Calculates the average incoming network traffic (bandwidth) per second for each container over a 5-minute window.
    * Result is in **bytes per second**.
